# Challenges

Pecorella's three parts cover production, derivatives, and
prestige. They cover _zero_ of what modern games call **challenge runs** —
opt-in resets where the rules of the game are deliberately worse, and
the reward for finishing is a permanent buff that bends the
post-challenge curve upward. The mechanic was rare in 2016 and is now
near-universal among long-running idle games.

The interesting design question is not _whether_ to add a hard mode but
_what shape of difficulty to add_. A challenge that simply slows the
production curve produces a slower version of the same loop — boring,
because the player's optimal strategy doesn't change. A challenge that
removes a generator tier, or shifts a cost exponent, or stacks
multipliers across runs, changes the _shape_ of the curve. The player's
strategy has to change with it.

The genre has settled on four genuinely different shapes. They aren't
variants of one pattern; each one mutates a different part of the
underlying model.

## Shape 1 — Single-completable, mechanic-mutating

The classic shape. Each challenge in a fixed list is a distinct rule
mutation: _disable this generator_, _change this cost formula_,
_replace this currency_. The player runs each once, finishes once, and
the slot's reward — usually an upgradeable autobuyer or a permanent
multiplier — is unlocked forever. The challenge itself is a piece of
content that gets _consumed_.

Antimatter Dimensions is the canonical example. Its normal challenges
include "buying Antimatter Dimensions or Tickspeed upgrades halts
production of all Antimatter Dimensions" (challenge 2), "the 1st
Antimatter Dimension is heavily weakened, but gets an uncapped
exponentially increasing multiplier" (challenge 3), and "buying an
Antimatter Dimension automatically erases all lower tier Antimatter
Dimensions" (challenge 4).
<Cite repo="AntimatterDimensionsSourceCode" path="src/core/secret-formula/challenges/normal-challenges.js" line="23-55" />
Each one breaks a specific assumption of the
base game's loop, forces the player to find a new strategy, and is
done forever once goal is reached.

<Cite repo="AntimatterDimensionsSourceCode" path="src/core/normal-challenges.js" line="95-112" />

```js
get isCompleted() {
  return (player.challenge.normal.completedBits & (1 << this.id)) !== 0;
}

complete() {
  player.challenge.normal.completedBits |= 1 << this.id;
  // ...
}
```

The completion state is a single integer's bitmask — one bit per
challenge. There is no completion _count_; once a bit is set it stays
set. Eternity Challenges in the same game push this further by adding a
small `maxCompletions` (typically 5),
<Cite repo="AntimatterDimensionsSourceCode" path="src/core/eternity-challenge.js" line="82-84" />
where each successive run requires
a higher goal and yields a stronger reward — a hybrid of single-
completable with a five-step ladder.

The math impact: each challenge changes the shape of one specific
sub-system. Disabling a generator is a topology change to the
[production graph](/modern/production-graphs); altering a cost scale
is a regime shift in the [cost-acceleration](/modern/cost-acceleration)
curve. The challenge ends and the change is gone — but the _reward_ (a
stronger autobuyer, a new modifier slot) shifts the whole post-challenge
curve upward.

## Shape 2 — Stackable debuff

Where AD's challenges are discrete one-shots, Synergism's
**corruptions** are a continuous additive ladder. Eight named
corruptions — viscosity, deflation, dilation, hyperchallenge,
illiteracy, drought, recession, extinction — each take an integer level
from 0 into the low teens.
<Cite repo="SynergismOfficial" path="src/Corruptions.ts" line="18-25" /> The ascension you run is parameterized by a _loadout_: a
levels-vector across all eight. Higher levels make the run harder; the
final run-score multiplier rewards harder loadouts.

<Cite repo="SynergismOfficial" path="src/Corruptions.ts" line="260-279" />

```ts
get totalCorruptionDifficultyScore () {
  let basePoints = 400
  Object.keys(this.#levels).forEach((key) => {
    basePoints += 16 * Math.pow(this.getTotalLevel(key as keyof Corruptions), 2)
  })
  return basePoints
}

#calcTotalScoreMult () {
  return productContents(
    Object.keys(this.#levels).map((key) => {
      const corrKey = key as keyof Corruptions
      return this.scoreMult(corrKey)
    })
  )
}
```

Two things stack at once. The _difficulty score_ is `400 + 16 · Σ
level²` summed across corruptions — a sum of squares, so a few
high-level corruptions dwarf many low-level ones, and the run gets
quadratically harder per level. The _score multiplier_ is the
**product** of per-corruption multipliers, structurally identical to
the [modifier chains](/modern/modifier-chains) covered earlier. Corruptions
are a modifier chain the player tunes
_against themselves_ — a knob that makes the run harder in exchange for
a bigger reward at the end.

The persistence is also different from AD. Corruption levels persist
across ascensions (the loadout you choose is the loadout that runs); you
can't "complete" a corruption, you can only push it higher. The design
question becomes "how high can I push it before the gate closes?" — a
softcap-shaped optimization rather than a checklist.

## Shape 3 — Parallel re-run

NGU Idle's challenge slots are a third shape: there are several
challenge tracks (basic, no-rebirth, laser-sword, blind, ND…), each is
re-runnable from scratch under a constraint, and each run gives a
proportional reward. The core mechanic isn't single-completable — many
runs are expected — but it isn't stacking either; each run is an
isolated re-execution of the base game loop with one knob disabled
("you cannot rebirth", "you cannot see your stats", "you have no
adventure-zone gear").

What this produces is _constraint-as-content_. The base game already
defined an optimal play loop; the challenge takes one input variable to
that loop and pins it. The player has to re-derive the optimal loop
without that input. The same time-investment math applies as
it does in runs, but the available actions are restricted, so the
optimum is a different policy altogether.

NGU's source isn't open, so this section runs without a citation, but
the shape is recognizable: it's the same "slot of re-runnable
challenges" pattern that recurs in smaller games (Trimps' world-tier
challenges, several Synergism singularity challenges), and it generally
co-exists with other shapes in the same game.

## Shape 4 — Challenge as content zone

The fourth shape doesn't graft a constraint onto the existing loop. The
challenge _is_ the content. Trimps' Spire is the clearest example: a
hand-built tower of fixed enemies with a custom defense-grid mini-game
on top, distinct currencies (Spirestones), and rewards for partial
clears. Unlike the previous shapes, you don't _complete_ a Spire run by
hitting the same goal as the base game with a debuff; you complete it
by finishing the _Spire's_ unique mechanic.

Trimps' two follow-up challenges, **Mayhem** and **Pandemonium**, push
this further by adding a per-completion difficulty escalation. Each
completion makes the next run harder by a fixed multiplier:

<Cite repo="Trimps" path="config.js" line="5639-5680" />

```js
Pandemonium: {
  // ...
  getEnemyMult: function() {
    return Math.pow(5, game.global.pandCompletions);
  },
  getTrimpMult: function() {
    return 1 + 0.1 + 0.1 * game.global.pandCompletions;
  },
  // ...
}
```

`getEnemyMult = 5^completions`. The fifth Pandemonium run is 625× as
hard as the first. The player's permanent reward grows additively (10%
per completion) while the next run's difficulty grows
_multiplicatively_ — which is the same `5^N` shape used in the
[cost-acceleration](/modern/cost-acceleration) page, redirected from
"how expensive is the next purchase" to "how strong are the next run's
enemies." The challenge becomes a [modified run](/modern/layered-prestige)
where the prestige reward and the prestige
difficulty climb together.

Pandemonium also progressively _removes_ equipment slots — every two
completions another armor or weapon slot becomes unavailable. The
challenge's content surface shrinks even as its difficulty grows.

## The combinatorial case — Realm Grinder

Realm Grinder doesn't fit any of the four shapes cleanly because it
combines them. (Its source is closed, so this is the design as its
community documents it rather than as read from code.) The R-challenges (Reincarnation challenges) are
single-completable like AD's, but the active _faction_ the player
chose at run start interacts multiplicatively with the challenge
constraint, which interacts further with research bonuses, which
interact further with whether the player has unlocked higher-ranked
factions. The result is a combinatorial design space: the same R5
challenge can be approached as Fairy + heritage A or as Demon +
heritage B and play out as two different optimization problems.

This is the design-space limit of the four shapes interacting.
Single-completable times stackable times tunable-loadout produces a
challenge surface where there's no clean "best strategy" — the player
finds a sequence of attempts that explores the combination space.

## What the math actually changes

The four shapes are not arbitrary. Each one mutates a _different
component_ of the underlying production model:

- **Single-completable challenges** typically alter the **production
  graph** topology — a tier disabled, an edge removed, a currency
  redirected. The effect on the curve is the polynomial-degree shift
  worked out in [production-graphs](/modern/production-graphs). The
  reward unlocks a new edge or a stronger node, undoing more than the
  challenge took away.
- **Stackable debuffs** are a [modifier chain](/modern/modifier-chains)
  the player tunes against their own production, with a `Σ level²`
  difficulty cost and a `Π effect` reward. The chain is structurally
  identical to a chain of positive modifiers, applied to the negative side.
- **Parallel re-runs** pin one input to the existing
  [optimal-policy](/modern/automation#three-policies-three-curves) problem and force the player
  to find a different policy that still satisfies the goal. The math
  isn't different; the constraint surface is.
- **Content-zone challenges** introduce an entire new
  [production system](/modern/production-graphs) with its own currencies
  and its own loop. The base game's math becomes a feeder for the
  zone's math.

Repeated runs (Pecorella's Part III) iterate the _same_ loop at higher
amplitudes. Challenges run _different_ loops. The reward structure on
top of either is the same — finish, gain something permanent — but the
content the loop produces is qualitatively different. Designers reach
for challenges when run-to-run escalation alone would feel
repetitive; players reach for them when the base loop's strategy has
become rote.

## Why the shape matters more than the mechanic

A "hard mode" that multiplies enemy HP by 10× is a slower version of
the same game. A challenge that disables tier 3 is a _different_ game,
because the player's optimal allocation across tiers 1-2-4-5 is
nothing like their optimal allocation across all five. The Synergism
corruptions ladder is yet another game, because the design lives in the
loadout — choosing _which_ corruptions to push and _how much_ — rather
than in any single run's play.

The genre's lesson, ten years after Pecorella, is that the production
math is most teachable, most replayable, and most intrinsically
interesting when it can be perturbed in _qualitatively different_
ways from the base loop. Repeated runs loop the math at higher
amplitude. Challenges loop the math under different _equations_. Both
are necessary; neither replaces the other.
